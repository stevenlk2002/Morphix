# PRD：企业微信应用会话正确显示名字和头像

## 项目信息

| 项 | 内容 |
| --- | --- |
| Language | 中文 |
| Programming Language | Python (FastAPI + SQLite) + React + TypeScript（沿用现有栈） |
| Project Name | `wecom_app_display` |
| 文档版本 | v1.0 |
| 关联协议 | iPad 协议 API 文档 第 20 节「获取应用 app 列表」 |

### 原始需求复述

企业微信渠道的会话/联系人列表中，部分条目显示为一串**裸数字**（如 `10223`、`13102694783555467`、`1688852792312821`），无名称、无头像。这些条目实际是**企业微信应用/小程序**（iPad 协议 `msg_type=3`）。需通过 iPad 协议「获取应用 app 列表」接口（`POST {base}/wxwork/getCorpWxApp`）拉取应用元信息，使其在**会话列表**和**聊天消息**中都能显示正确的名称与头像。

## 二、产品目标

1. **消除裸数字**：企业微信渠道内所有应用类条目（`msg_type=3`）在会话列表与聊天界面中，均以**真实应用名称 + 应用头像**呈现，不再出现无意义的数字 ID。
2. **可识别、不误导**：用户能一眼区分「应用/小程序」与「真人联系人/群聊」，并明确知道应用会话为只读通知流、不可回复。

### P0（必须有）

| ID | 需求 | 说明 / 验收要点 |
| --- | --- | --- |
| P0-1 | **新增协议封装** `get_corp_wx_app(uuid)` | `POST {base}/wxwork/getCorpWxApp`，入参 `{uuid}`；解析 `data.wxAppList[]`；沿用现有 `_post()` 的超时与 `errcode` 归一化约定；协议失败抛现有异常类型，不阻断其余同步路径 |
| P0-2 | **应用信息落库** | 存储 `appId`、`appOpenId`、`corpid`、`name`、`imgId`(头像 URL)、`appType`、`desc`、`homeInfo`、`lastModTime`；建表/建列须走 `migrate_schema` 幂等模式（见 F9）；按 `account_id` 隔离 |
| P0-3 | **同步流程接入第五路** | `run_full_sync(account_id)` 增加应用列表拉取；**顺序须在会话列表规范化之前**（否则首轮同步仍拿不到名称）；单路失败不影响其余四路（与现有容错一致） |
| P0-4 | **修复 `_normalize_session` 应用分支** | `msg_type==3` 时：① 按应用 ID 匹配取 `name`；② `contact_id` 置 `None`（修 F4）；③ 命中失败才回退 raw sessionid |
| P0-5 | **解除应用会话过滤** | 移除/改写 `list_sessions` 的 `WHERE cs.msg_type != 3`（F5）；**前提是名称与头像已能正确解析**，否则维持过滤（避免回归到「显示数字」的更差状态） |
| P0-6 | **会话列表显示应用名称 + 头像** | 查询增加 LEFT JOIN 应用表，`COALESCE` 链扩展为 `联系人 → 群 → 应用 → 会话名`；头像同理 |

| P0-8 | **应用会话只读态** | 前端识别 `sessionType === '应用'`（或 `msgType===3`）时禁用输入框与发送按钮，展示「应用通知会话，不支持回复」提示，避免触发 F8 的 400 报错 |
| P0-9 | **数据回填** | 已入库的存量应用会话，在下一次全量同步后名称与头像应被纠正（UPSERT 而非仅 INSERT） |

## 五、UI/UX 设计稿描述

### 5.1 会话列表中的应用卡片

沿用现有会话行布局（`ChannelSessions.tsx` L598 的 `<Avatar size={40}>`），仅在以下三处差异化：

| 元素 | 规格 |
| --- | --- |
| **头像** | 40×40，**圆角矩形（radius 8px）**，与真人/群聊的圆形头像形成视觉区分；图源 `imgId`；加载失败回退应用名首字色块 |
| **名称** | 位置不变（头像右侧第一行），显示应用 `name`；超长省略号截断 |
| **类型标签** | 名称右侧紧跟一枚小徽标「应用」（或 P1-3 的「小程序」），弱色浅底，字号小于名称 |
| **副标题行** | 显示最近一条通知摘要；无消息时显示应用 `desc` 截断 |
| **未读数** | 与现有一致，右侧红点/数字 |
| **托管开关** | 应用会话**不展示**托管相关控件（不可托管、不可发消息） |

> 关键：圆角矩形 vs 圆形，是用户区分「应用」与「人」的第一视觉锚点，成本极低、收益明显。

### 5.2 聊天面板中的应用会话

| 区域 | 规格 |
| --- | --- |
| **顶部标题栏** | 应用头像（圆角矩形，小尺寸）+ 应用名称 + 「应用」徽标；隐藏/置灰「机器人托管」下拉 |
| **消息气泡** | 应用消息一律为 inbound（左侧）；气泡左侧头像取应用 `imgId`，形状同为圆角矩形，与列表保持一致 |
| **发送者名称** | 群聊场景下才显示发送者名；应用为 1:1 通知流，气泡上方可不重复显示名称 |
| **底部输入区** | **整体禁用**：输入框置灰 + `placeholder`「应用通知会话，暂不支持回复」；发送/附件按钮隐藏或禁用 |
| **空态** | 无消息时显示「暂无应用通知」 |

### 5.3 视觉一致性约定

- 应用头像形状（圆角矩形）在**会话列表、聊天标题栏、消息气泡**三处必须完全一致。
- 兜底占位符使用应用名首字，**绝不允许再回落到裸数字 ID**——这是本需求的核心验收红线。

## 六、待确认问题

| # | 问题 | 背景与建议 |
| --- | --- | --- |
| **Q1** | **`sessionid` 到底对应 `appId` 还是 `appOpenId`？** | 协议示例中 `appOpenId=1000015`（小数值）、`appId=5629499961733838`（大数值）。而用户截图里的三个 ID 形态**并不统一**：`10223`（小，形似 appOpenId）、`13102694783555467`（大，形似 appId）、`1688852792312821`（形似企微 vid）。**建议**：① 落库时 `appId` 与 `appOpenId` **都建索引**，匹配时按 `sessionid == appId OR sessionid == appOpenId` 双键命中；② 先取一次真实账号数据做对拍验证。若 `1688852792312821` 两个键都命中不了，说明它可能是内部联系人 vid 而非应用，需另行归类。 |
| **Q2** | **落 `channel_contacts` 还是新建 `channel_apps` 表？** | **建议新建 `channel_apps` 表**。理由：① 应用有 `appType`/`homeInfo`/`corpid`/`lastModTime` 等联系人语义没有的字段，塞 `extra_json` 会牺牲可查询性；② 应用不可聊天、不可托管、不进客户档案，混入 `channel_contacts` 会污染联系人数与客户统计；③ 现有 avatar JOIN 已是「联系人 / 群」双路（F6），加第三路 `channel_apps` 与既有架构最自洽。**需主理人拍板确认。** |
| **Q3** | **消息中应用发送者头像如何解析？** | 现有 `_resolve_sender_avatar` 按 `sender_id` 查 `channel_contacts`（F7），应用必然落空。**建议**：优先按会话维度解析——先由 `conversation_id` 取 `remote_session_id` 与 `msg_type`，当 `msg_type==3` 时直接走应用表，而非依赖可能为空/异形的 `sender_id`。需确认应用消息的 `sender_id` 实际取值形态。 |
| **Q4** | **裸数字究竟出现在「会话列表」还是「联系人列表」？** | 用户描述为「好友列表栏」，但代码中会话列表已过滤 `msg_type != 3`（F5）——这意味着截图中的数字**可能来自联系人列表**（`GetInnerContacts` 把应用当内部联系人返回），或来自未走该过滤的其他查询路径。**建议开发前先复现定位**，若联系人列表也受影响，P0 范围需相应增加「联系人列表中的应用识别与剔除/正确显示」。 |
| **Q5** | **应用列表拉取频率与配额** | `getCorpWxApp` 无分页参数、疑似一次性返回全量。若企业应用数量大或接口有频控，每次全量同步都拉取可能不经济——是否直接在 P0 就采用 P1-1 的 TTL 策略？ |

## 七、验收标准（Definition of Done）

1. 企业微信渠道会话列表中，**不存在**任何以裸数字为名称的条目。
2. 应用会话显示正确的应用名称、应用头像（圆角矩形）与「应用」徽标。
3. 打开应用会话，消息气泡头像为应用图标；输入区禁用并有明确文案提示。
4. 应用改名后，下一次同步（或 TTL 到期刷新）能自动更新列表中的名称与头像。
5. 应用列表接口异常时，其余四路同步仍正常完成，且列表**降级为应用名兜底**而非崩溃或回退到数字。
6. 现有真人联系人、群聊会话的名称与头像展示**无回归**。
